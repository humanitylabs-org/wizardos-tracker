# Wizard OS Tracker (app id `board`): plan and Reuse

One sentence: humans manage Wizard development as GitHub Goals and Bugs in one screen; agents report bugs, comment and write PRs.

Visible actions (0.6): sign in with your own GitHub token; Goals | Bugs switch; the Wizard OS Builder switch (mock-up, `GET/POST /api/builder`, `data/private/builder.json`, default Paused); the workflow row of three hand-off steps 1 Open (count queued) → 2 Build (building) → 3 Review (ready-to-test), then Done (closed, all time), each with a role line and a tap-for-who sheet, with "Doesn't work → back to Build" (return arrow) and "Works → the opener closes it" under it; five bottleneck stats (third is "Waiting for review"); Everyone ▾ and All repos ▾ (multi-select sheet, per-view localStorage `board.repos.goals|bugs`); Works / Doesn't work on Waiting for review cards opened by someone else (cards you or your own agent opened say "Someone else reviews this"); tap any row to read the issue in a sheet with "Opened by X · reviewed by anyone else on the team". Rows are NOT links (`tapTarget()`), because the native Wizard app sends any tap on an external href to the browser; only Open on GitHub in the sheet links out. The 0.5 policy strip is gone.

Visible actions (0.7, Miguel: 0.6 was "correct but too noisy"; numbers and arrows are the main thing): Goals | Bugs + a small Builder switch on one row (turning it on shows an anchored "Not connected to the builder yet" and it stays Paused; no always-visible note); the assembly line Queued → Building → Review → Done (four bins, big number + one word, prominent arrows, a text-less curved return arrow Review → Building; no role lines, no Works/Doesn't-work text lines; tapping a bin shows an anchored popover with who + one sentence, Review says "not whoever opened it"); small stats (Queued for, Build time, In review, Tries, Kicked back); two identical pills Everyone ▾ / All repos ▾, each an inline anchored checklist (multi-select, counts, All reset; author filter now multi-select; per-view localStorage `board.who.*`, `board.repos.*`); groups Review / Building / Queued with small headings. Bug rows: title + 1 clamped description line + repo · opener · comments (titles are never rewritten; the issue reset cleans them). Try it switch (mock-up) on every row and Review card: `aria-disabled` outside Review (tap → "Can be switched on once it's in Review"), in Review it POSTs `/api/try {repo, number, on}` (per person in `data/private/try.json`, last 500) and shows the mock-up note; it stops propagation so the row never opens. The repo and step sheets are gone; one `#pop` element serves every popover. MCP: `try_status`, `try_set` (owner_request).

Visible actions (0.8, Miguel: numbers and arrows stay the main thing): the stats row moved INTO the assembly line and is deleted. Each bin = big count, its word + a small ⓘ (the who/what popover), and under it a tiny avg (Queued: opened → first building; Building: first building → ready-to-test; Review: ready-to-test → close or kick-back per stint; Done: opened → closed) with an inline-SVG box-and-whisker (min, p25, median, p75, max; log scale; strokes `--ink-3`/`--ink-2`, median `--accent`) at 3+ points, else the avg or —. The return arrow carries `rate · per-item` kick-backs (tap/hover for the sentence + avg first kick-back → done). Tapping a bin filters the list to that stage (toggle; `.sel` highlight, others `.dim`; a `Stage ✕` pill in the filter row clears); Done loads `GET /api/done?view=` (closed, newest first, ≤50) into a Done group. Author/repo filters recompute line counts and stats client-side (`lineStats()` mirrors server `line_stats()`); the stage filter never changes the line. Detail sheet: the same mini line for the one item from `GET /api/flow?repo=&number=` (REST timeline, ≤3 pages, cached 2 min server side, 60 s client side): time spent per stage, Done date, kick count on the return arrow, current stage highlighted, `Queued for Nd` and dimmed rest when there is no stage history. MCP `board_flow`. Server: `history_of(ev, opened, closed_at, state)` is the single state machine both the stats search (GraphQL timelineItems) and `/api/flow` (REST timeline) feed; `/api/stats` items gained `review_rounds`, `total`, `kick_to_done`, `stage`, `staged`, `opened_at`, `closed_at` and `summary.line`.

Visible actions (0.9, Miguel: the box-and-whisker was hard to read; add targets; chips not dropdowns): each bin's stat = three tiny numbers (p25, **median**, p75) over a 60-unit inline-SVG bar (track `--line-2`, p25–p75 segment `--ink-3`, median dot, target tick `--accent`, log scale spanning range and target) and a `target 1h` line; median coloured `--wz-success`/`--wz-warning` (the `-light` pair in light, same as kit `.wz-pill.ok/.warn`). Targets: `POLICY_DEFAULT['targets']` (Bugs 1h/4h/1d/2d, Goals 1d/3d/3d/14d), `policy.json` `targets` overrides (seconds or `30m`/`4h`/`3d`/`2w`, unknown keys ignored), in `/api/policy` and `/api/split` (`targets`). ⓘ adds typical range, median and `Target: under X`. Filters: Goals none; Bugs = Who chips + Repo chips (all non-archived org repos via `GET /orgs/{org}/repos?type=all` paged, cached 1 h per token/org, `/users/{org}/repos` fallback for a personal account; zero-count chips dimmed; top 10 (5 under 640 px) with bugs + picked, `+N more`/`Less` inline). Sort (Bugs): segmented Oldest | Newest | Most discussed | Recently active, default Oldest, `localStorage board.sort.bugs`, applied inside each group, hidden on the Done stage. Bug rows/Review cards show age. Done rows lose the Try it switch. Dropdown checklists (`.bd-f`, `.bd-fp`) are gone.


Policy (0.6): `POLICY_DEFAULT` in server.py = `team` [{name, logins, agents:[{login,name}]}], `builder` {name, logins}, `open` {goals: ['James'], bugs: 'team'}; `DATA_DIR/policy.json` overrides any key. `person_of(login)` maps a login (person or agent, case-insensitive) to a team name; `same_person()` drives `mine` in `/api/split` and the 403 in `/api/test/works|fails`. `/api/split` returns `steps` (built by `steps_for(view)`) and each card's `opener`; `/api/detail` returns `opener`. `GET /api/policy` returns team, builder, open, steps {goals, bugs}, me {login, person} and the 0.5 keys (goals.authors, builds.builders, lines).

Data (0.5): `GET /api/split` uses the same paged search, now also asking `assignees(first: 10)` and `comments { totalCount }` (so rows carry owners, comment count and `desc` without extra calls). Bottleneck stats (`GET /api/stats?view=&author=&repos=`): one search over every issue of that kind (open and closed, 100 a page, up to 600) with `timelineItems(LABELED_EVENT, UNLABELED_EVENT, CLOSED_EVENT, REOPENED_EVENT)`, reduced per item to wait/build/tries/kicks/waiting_for and cached 5 minutes per account and view. `/api/split` includes them when cached, else `stats: {pending: true}` and the view calls `/api/stats` right after (bugs history takes ~8 s cold). The view filters items by author and repos and averages itself, so the pipeline, stats and lists always agree.

Why 0.6: Miguel found the 0.5 policy strip unclear; he wanted the workflow itself shown as three steps, a hot potato passed between people and the builder, merged with the stage counts into one row, with exactly who may do each step and the "not the opener" review rule enforced. He will use this screen to explain the workflow to the team.
Why 0.5: Miguel wanted the goal rows readable at a glance (description, owners, comments), James's workflow stages named Queued → Building → Waiting for human with where work waits, the who-may-do-what policy, a builder on/off switch to wire later, and a repo filter beside Everyone.

Why 0.3: Miguel rejected 0.2 (Issues tab and repo filter pointless, Goals tab off to the side, no New button wanted, no logged-in line). He asked for "just goals and then bugs", each with things to test.
Why 0.4: Miguel liked 0.3 and the flat Bugs list but wanted to read issues without leaving the app, see real status (building vs queued) with counts, filter by who wrote it, and never lose items past 80.
