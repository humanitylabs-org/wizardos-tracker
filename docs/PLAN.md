# WizardOS Tracker (app id `board`): plan and Reuse

One sentence: humans manage Wizard development as GitHub Goals and Bugs in one screen; agents report bugs, comment and write PRs.

Visible actions (0.6): sign in with your own GitHub token; Goals | Bugs switch; the WizardOS Builder switch (mock-up, `GET/POST /api/builder`, `data/private/builder.json`, default Paused); the workflow row of three hand-off steps 1 Open (count queued) → 2 Build (building) → 3 Review (ready-to-test), then Done (closed, all time), each with a role line and a tap-for-who sheet, with "Doesn't work → back to Build" (return arrow) and "Works → the opener closes it" under it; five bottleneck stats (third is "Waiting for review"); Everyone ▾ and All repos ▾ (multi-select sheet, per-view localStorage `board.repos.goals|bugs`); Works / Doesn't work on Waiting for review cards opened by someone else (cards you or your own agent opened say "Someone else reviews this"); tap any row to read the issue in a sheet with "Opened by X · reviewed by anyone else on the team". Why 0.10: Miguel saw the Who row reshuffle when tapping repos, wanted goal ownership visible at a glance with real names, wanted to tune targets from the screen (same for everyone), and flagged ⓘ inside a tappable bin as a nested click.

Policy (0.6): `POLICY_DEFAULT` in server.py = `team` [{name, logins, agents:[{login,name}]}], `builder` {name, logins}, `open` {goals: ['James'], bugs: 'team'}; `DATA_DIR/policy.json` overrides any key. `person_of(login)` maps a login (person or agent, case-insensitive) to a team name; `same_person()` drives `mine` in `/api/split` and the 403 in `/api/test/works|fails`. `/api/split` returns `steps` (built by `steps_for(view)`) and each card's `opener`; `/api/detail` returns `opener`. `GET /api/policy` returns team, builder, open, steps {goals, bugs}, me {login, person} and the 0.5 keys (goals.authors, builds.builders, lines).

Data (0.5): `GET /api/split` uses the same paged search, now also asking `assignees(first: 10)` and `comments { totalCount }` (so rows carry owners, comment count and `desc` without extra calls). Bottleneck stats (`GET /api/stats?view=&author=&repos=`): one search over every issue of that kind (open and closed, 100 a page, up to 600) with `timelineItems(LABELED_EVENT, UNLABELED_EVENT, CLOSED_EVENT, REOPENED_EVENT)`, reduced per item to wait/build/tries/kicks/waiting_for and cached 5 minutes per account and view. `/api/split` includes them when cached, else `stats: {pending: true}` and the view calls `/api/stats` right after (bugs history takes ~8 s cold). The view filters items by author and repos and averages itself, so the pipeline, stats and lists always agree.

Try it (0.14.0, Miguel): the **Try it** switch on a Human review row is the change's real **feature switch on the Wizard you are looking from** — the same state as Settings › Appearance › Try new features (one shared state, `Pages/wizard-look/look.json` `tweaks`). The Tracker's page runs inside the owner's Wizard, on the shell's origin, so the browser calls the shell's owner-only same-origin route `GET/POST /wizard-os-home/store-install/_feature-switches` (wizard-app-manager `StoreHandler`, owner Tailscale login; POST also sends `X-Wizard-Store: 1`; body `{"id": "<author>/<id>", "on": bool}`). No app key, no container networking, nothing to install. Messages: on For everyone (`locked`, or a 409) "Switch to For testers in Settings to try this"; the switch is not in this box's catalog, or the box's App Manager has no route yet (404) "Update to try this"; opened outside a Wizard (no JSON answer) "Open the Tracker inside your Wizard to try this."; no switch named "This change has nothing to switch on.".
**`Switch:` convention (builder hand-over):** the builder's "What to check" comment (the one that hands the item to AI review / Human review) ends with one line `Switch: <author>/<id>` naming the shell tweak id the change sits behind (e.g. `Switch: miguel/send-and-go`; the id in wizard-ux `wizard-os-home/tweaks/catalog.json`). The newest builder comment with such a line wins; a `Switch:` line in the issue body is the fallback; no line = nothing to switch. The server parses it (`switch_of()`, `SWITCH_LINE`) and serves it as `switch` on Human/AI review cards; Markdown emphasis or backticks around it are fine. The server-side `GET/POST /api/try` and MCP `try_status`/`try_set` still only record a per-person wish (mock-up); the view no longer calls them.
