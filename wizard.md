# WizardOS Tracker

Display name "WizardOS Tracker". 0.12 (store listing): the app id follows the name, `wizard-os-tracker`, with `renamed_from: [board]`, so `wam app-rename board` moves an installed `board` (data, sign-ins, port, settings) to the new id; the repo stays `oscarhenrycollins/wizardos-tracker`. 0.13.7: the product is spelled WizardOS (one word), so the id became `wizardos-tracker` and the name `WizardOS Tracker`, with `renamed_from: [board, wizard-os-tracker]` (`wam app-rename wizard-os-tracker wizardos-tracker` moves an installed copy; agent tools are now `mcp__wizard__wizardos_tracker__*`).

Humans manage the work; agents write the PRs. Board shows two kinds of GitHub issue across one organisation (default `humanitylabs-org`):

- **Goal** (label `goal`): a big outcome with a short done-list (a markdown task list). Only humans open and close goals.
- **Bug** (label `bug`): small and specific. Anyone may report one; agents start only after a human accepts it (label `accepted`).

Each person on the WizardOS team (active members of `humanitylabs-org`) connects their own GitHub account with a personal access token; anyone can install it, only team members can use it (0.12). The token is kept on the box only (file mode 0600), validated with `GET /user`, never returned to the view or MCP. Board sees exactly what that token can see. GitHub is the only backend: the app keeps no copy of issues, only a 60-second read cache.

In the app (0.7, minimalist: numbers and arrows first), top to bottom: a small **Goals | Bugs** switch with a small **Builder** switch on the same row (Paused / Running; a mock-up stored at `GET/POST /api/builder`, default Paused; trying to turn it on shows a small anchored note "Not connected to the builder yet" and it stays Paused; if it was Running it can be paused); the **assembly line**, one row of four bins **Queued → Building → Review → Done**, each a big number with one word, clear arrows between, and a small curved return arrow (no text) from Review back to Building (Doesn't work). Queued = open, not `building` or `ready-to-test`; Building = label `building`; Review = label `ready-to-test`; Done = closed, all time. Tapping a bin shows a small anchored popover: who does that step and one sentence (Queued: Goals = James, Bugs = anyone on the team; Building: WizardOS Builder `wizardosbuilder`; Review: the team, not whoever opened it, a person and their own agent counting as one; Done: the opener closes it once it works). The team roster and who opens each view are defaults in code, overridable in `DATA_DIR/policy.json` (keys `team`, `builder`, `open`), served at `GET /api/policy`. Then one small row of bottleneck stats from GitHub label history (Queued for = opened → first `building`; Build time = first `building` → first `ready-to-test`; In review = average and longest age of items now `ready-to-test`; Tries = times labelled `ready-to-test`; Kicked back = `ready-to-test` removed without a close or `approved`), cached 5 minutes, — until there is data. Then (0.9, Bugs only) Who and Repo chip rows, remembered on the device (`board.who.bugs`, `board.repos.bugs`); bins, stats and lists honour both. Lists are grouped **Review** (cards: what to check from the builder, repo · opener · comments, Works / Doesn't work: comment, drop `ready-to-test`, on Works add `approved`, never close; hidden on items you or your own agent opened, and refused by the server), **Building** and **Queued**. Goal rows: title, comment count, description (2–3 lines), progress bar, owners · repo. Bug rows: title, one line of description, repo · opener · comment count. Titles are shown as written. Every row and Review card has a small **Try it** switch on the right (mock-up): greyed except in Review, where flipping it records the choice per signed-in person (`GET/POST /api/try {repo, number, on}`, `DATA_DIR/private/try.json`) and shows "Mock-up: this will switch the change on in your Wizard once it runs a build with it"; a greyed one says "Can be switched on once it's in Review". The switch never opens the row. Rows are not links: tapping opens the issue in an in-app sheet (body and comments as GitHub renders them, cleaned on the box), and only its Open on GitHub link leaves the app. No create or refresh UI; one tiny account control (0.12.2). Agents use the MCP tools (`board_list`, `board_get`, `board_report_bug`, `board_comment`, `builder_status`, `try_status`; `board_add_goal`, `board_accept_bug`, `board_close`, `board_reopen`, `builder_set`, `try_set` only on a human's explicit request, and never to close or reopen goals).

0.8 (Miguel: keep it minimal, numbers and arrows first): the separate stats row is gone; each bin carries its own tiny stat under its word: Queued = avg time queued (opened → first `building`), Building = avg build time (first `building` → `ready-to-test`), Review = avg time in review (`ready-to-test` → close or kick-back, per stint), Done = avg total time (opened → closed), each with a tiny inline-SVG box-and-whisker (min, p25, median, p75, max, log scale, kit colours) from 3 data points, else just the avg or —. The return arrow Review → Building carries the kick-back label `rate · per-item` (e.g. `40% · 1.5×`: share of reviewed items kicked back at least once, average kick-backs among those); tapping it says so plus the average time from first kick-back to done. A small ⓘ next to each bin word shows the who/what popover; tapping the bin itself filters the list to that stage (toggle, the bin highlighted and the others dimmed, a `Stage ✕` pill clears it). The Done bin lists the most recently closed items of that view (`GET /api/done`, up to 50, newest first) in a Done group. Everyone/repo filters recompute the counts and stats (client-side over `/api/stats` items); the stage filter never changes the line. 0.9 (Miguel: the box-and-whisker was hard to read): each bin's stat is now a readable mini range: three small numbers (p25 left, the median bold in the middle, p75 right; one point or two shows just the median), a thin bar from p25 to p75 with a dot at the median, and a short line `target 1h`. Bug rows and Review cards show the bug's age (`12d`). Done rows have no Try it switch.

Try it (0.14.0, Miguel): the **Try it** switch on a Human review row is the change's real **feature switch on the Wizard you are looking from** — the same state as Settings › Appearance › Try new features (one shared state, `Pages/wizard-look/look.json` `tweaks`). The Tracker's page runs inside the owner's Wizard, on the shell's origin, so the browser calls the shell's owner-only same-origin route `GET/POST /wizard-os-home/store-install/_feature-switches` (wizard-app-manager `StoreHandler`, owner Tailscale login; POST also sends `X-Wizard-Store: 1`; body `{"id": "<author>/<id>", "on": bool}`). No app key, no container networking, nothing to install. Messages: on For everyone (`locked`, or a 409) "Switch to For testers in Settings to try this"; the switch is not in this box's catalog, or the box's App Manager has no route yet (404) "Update to try this"; opened outside a Wizard (no JSON answer) "Open the Tracker inside your Wizard to try this."; no switch named "This change has nothing to switch on.".
**`Switch:` convention (builder hand-over):** the builder's "What to check" comment (the one that hands the item to AI review / Human review) ends with one line `Switch: <author>/<id>` naming the shell tweak id the change sits behind (e.g. `Switch: miguel/send-and-go`; the id in wizard-ux `wizard-os-home/tweaks/catalog.json`). The newest builder comment with such a line wins; a `Switch:` line in the issue body is the fallback; no line = nothing to switch. The server parses it (`switch_of()`, `SWITCH_LINE`) and serves it as `switch` on Human/AI review cards; Markdown emphasis or backticks around it are fine. The server-side `GET/POST /api/try` and MCP `try_status`/`try_set` still only record a per-person wish (mock-up); the view no longer calls them.
